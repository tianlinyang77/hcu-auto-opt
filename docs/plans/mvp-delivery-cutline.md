## 收口目标

优先证明一个受控候选能完成：来源可追溯 → 真实构建 → 结果原子入库 → 正确性 →
性能验证/拒绝 → 页面查看依据 → 人工签核。先固定一个现有目标和工作负载，不扩框架适配。

已有 M1 结果页与新 M2 Formal 入口分开展示。历史验收不能代替新入口的当期实机证据。
“系统能运行”与“候选获得加速”分开验收；候选被正确拒绝同样是功能链路结果。

## 剩余必做，按依赖排序

1. 构建 Worker 收口：执行日志、预算预留/结算、成功和失败归档；串联现有 Builder 与 Store。
2. 正确性与评测推进：真实证据接既有判断器，完成 Family 冻结和授权内执行；禁止人工改状态通关。
3. 一轮联合验收：实际候选加载/恢复、结果页、人工签核和重启读取；保留拒绝原因及原始证据。
4. 交付封版：待审代码完成评审/合入，固定版本、启动方式、复现步骤和已知限制。

本轮先补候选进度只读投影，让操作者能看到当前落库状态和制品编号。
这不代表上述四项已完成，不新增页面执行权限。

## 本次暂不扩展

多机、多框架、自动发布、自进化、新的调度策略、视觉重设计。
不新增第二套 Harness、判断器或签核体系。已有默认关闭、授权、停止及恢复边界保留。

## 对外可讲的内容

逐项给出“已验证 / 未验证 / 待接线”和证据链接，不给没有测试支持的完成百分比。
正式端到端未跑通前，只交付已验证模块与历史结果展示，不宣称一键自动优化已完成。
